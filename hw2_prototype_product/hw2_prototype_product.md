# Домашнее задание №2: Создаем прототип продукта

**Проект:** Интеллектуальный сервис нормализации и классификации мастер-данных (MDM)

### 1. Ключевые гипотезы
Для эффективной проверки прототипа мы разбиваем бизнес-логику на две независимые гипотезы:

* **Гипотеза 1 (Про качество классификации - ML):** Если мы предложим экспертам НСИ сервис автоматической NLP-классификации на базе языковой модели (сценарий проверки новых заявок на закупку), то мы получим метрику F1-weighted не менее 0.85 в течение тестового месяца, потому что модель способна улавливать неочевидные семантические паттерны в "грязных" текстах лучше, чем регулярные выражения.
* **Гипотеза 2 (Про скорость бизнес-процесса - Product):** Если мы внедрим API-интерфейс для пакетной обработки строк, то среднее время первичной маршрутизации заявки сократится с 15 минут до 2 секунд, потому что алгоритм мгновенно отфильтровывает очевидные категории, оставляя человеку только сложные аномалии.

### 2. Ключевые метрики
* **Продуктовые метрики:** * *Automation Rate:* Процент заявок, обработанных без участия человека (Target: >80%).
  * *Time-to-Resolve:* Время на классификацию одной записи (Baseline: ручной поиск ~3-5 минут; Target: <1 секунды).
* **Технические (ML) метрики:** * *F1-weighted:* Баланс точности и полноты в условиях сильного дисбаланса 79 категорий (Target: $\ge 0.85$). Замеряется на отложенной (Hold-out) тестовой выборке.
  * *Inference Latency:* Задержка ответа сервиса (Target: < 200 мс на запрос).

### 3. Что входит в прототип (Scope)
* **Входит:** * Пайплайн предобработки и очистки текста.
  * Обученная NLP-модель классификации.
  * REST API интерфейс для приема сырого текста и выдачи `category_id`.
* **Намеренно НЕ делаем:** * Полноценный Frontend/UI интерфейс. Причина: для проверки гипотезы качества классификации интерфейс не нужен, достаточно отправлять запросы в API (например, через Postman или скрипт).
  * Интеграцию в контур 1С на стороне заказчика. Причина: слишком высокие риски инфобезопасности на раннем этапе, тестируем локально.

### 4. Инструменты и готовые блоки
* **Моделирование:** Предобученная модель семейства `RuBERT` (например, `RuBERT-tiny2`) из Hugging Face. Использование готовой LLM/NLP архитектуры критично для понимания русскоязычной специфики промышленных товаров без необходимости обучать нейросеть с нуля.
* **Валидация и API:** Фреймворк `FastAPI` для обертки инференса и `Pydantic` для жесткой валидации входящих типов данных.
* **Работа с данными:** `pandas`, `scikit-learn` для Stratified K-Fold валидации.

### 5. Главный риск прототипа
Критический дисбаланс данных ("длинный хвост") и наличие шума в исторической разметке. Если мажоритарные классы перетянут на себя веса модели, она начнет игнорировать узкоспециализированное оборудование. Риск проверяется внедрением кастомных функций потерь (Class-balanced loss) и строгой стратифицированной валидацией.

### 6. Критерии остановки теста
* Если на тестовой выборке после подбора гиперпараметров метрика $F1 \text{-weighted} < 0.60$. Это будет означать, что сырые данные из 1С не содержат достаточного семантического сигнала для классификации, и проект нужно откатывать на стадию пересмотра сбора данных.
